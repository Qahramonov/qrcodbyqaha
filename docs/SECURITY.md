# Безопасность Chat helper — модель угроз и отчёт

Документ описывает, что защищается, как, чем это проверено и какие риски остаются. Статусы проверки: **[тест]** — покрыто автотестом (см. [TEST_REPORT.md](TEST_REPORT.md)), **[код]** — реализовано, проверено ревью кода, **[устройство]** — требует проверки на телефоне.

## 1. Активы
| Актив | Где хранится |
|---|---|
| `BOT_TOKEN` | только `backend/.env` (права 600, в `.gitignore`) |
| Ключи AI-провайдеров | только `backend/.env` |
| Серверный секрет (HMAC) | `backend/data/secret.key` (генерируется при первом запуске, права 600) |
| Токены приложения | БД — только HMAC-хеши; телефон — Android Keystore (AES-256-GCM) |
| Переписка/превью, память AI | SQLite `backend/data/chat_helper.db`, срок хранения настраивается |
| Платежи Stars | БД, идемпотентно по `telegram_payment_charge_id` |

## 2. Секреты
* Токен **не встроен** ни в исходники, ни в APK, ни в документацию, ни в тесты (тесты используют пустой токен и фейковую сессию Bot API). **[тест]** Скан репозитория и распакованного APK по шаблонам токенов Telegram/OpenAI/Gemini/Anthropic и приватных ключей — совпадений нет (см. TEST_REPORT §4). Найденный при аудите дефект — маскировщик пропускал токен, «склеенный» с `bot` в URL (`…/bot<token>/getMe`) — исправлен и покрыт тестом.
* Логи проходят через `Redactor`: маскирует токены ботов (`123456:ABC…`, в т.ч. внутри URL), `sk-…`, `AIza…`, `?key=…`, `cha_/chr_`-токены, `Bearer …`, а также точные значения секретов из `.env`. **[тест]**
* `python main.py --check` и `/api/v1/admin/system` выдают только «set / missing» для секретов (`public_summary`). **[код]**
* Приложение никогда не получает токен бота; оно работает только с API Chat helper.

## 3. Идентификация и роли
* **Super Admin** — единственный пользователь, чей Telegram ID равен `SUPER_ADMIN_ID` (8053614984). Роль вычисляется на сервере при каждом запросе; изменить её через API/БД-эндпоинты нельзя (`set_role` отказывает). Username (`@libPM`) не используется для авторизации. **[тест]**
* Telegram-апдейты: `from_user.id` проставляет Telegram, подделать его через Bot API нельзя. Команды бизнес-чата выполняются **только** если отправитель — владелец подключения (`from_user.id == connection.user.id`); сообщения собеседников, похожие на команды, игнорируются. **[тест]**
* API: личность берётся **только из сессии**, к которой привязан bearer-токен. Ни один эндпоинт не принимает `user_id` как доказательство личности; передача чужого ID обычным пользователем → `403 forbidden` (`scope_user`). Админ-эндпоинты требуют роль на сервере. **[тест]** — тесты «подстановка ID» и «пользователь → админ-эндпоинт» возвращают 403.
* Модератор назначается только Super Admin. Заблокированный пользователь теряет доступ к API сразу (проверка `is_restricted` при каждом запросе). **[тест]**

## 4. Привязка приложения (pairing)
* Код выдаётся **только в личном чате с ботом** (`/app`) — Telegram уже аутентифицировал пользователя. Пароли, коды входа Telegram и session-файлы **не запрашиваются и не используются**.
* 8 символов из 32-символьного алфавита (≈1.1·10¹² вариантов), `secrets.choice`, TTL 5 минут, одноразовый, в БД — HMAC-SHA256. **[тест]**
* Ограничения перебора: по IP 5/мин и 20/час; глобальная блокировка привязки на 15 минут после 50 неудачных попыток за 10 минут (уведомление Super Admin); не более 6 кодов в час на пользователя, новый код аннулирует предыдущий. **[тест]**
* Новое устройство → уведомление владельцу в Telegram; журнал входов и отчёт по подозрительным IP в приложении (Security). **[тест]**

## 5. Токены и сессии
* Непрозрачные случайные токены: access `cha_…` (32 байта, 1 час), refresh `chr_…` (48 байт, 30 дней). В БД — только HMAC-хеши. **[тест]**
* Refresh с ротацией: старый refresh-токен после использования недействителен (атомарный `UPDATE … WHERE refresh_hash=?`). **[тест]**
* Отзыв сессии/всех сессий, выход; максимум 10 активных сессий на пользователя. **[тест]**
* Лимит 240 запросов/мин на сессию + лимиты по IP в middleware. **[тест]**

## 6. Сетевая поверхность
* API слушает **127.0.0.1:8787**. Публичный адрес принимается только при `API_REMOTE_ENABLED=true` **и** наличии `API_SSL_CERTFILE` + `API_SSL_KEYFILE`; иначе адрес принудительно меняется на 127.0.0.1 (pairing-коды и токены не передаются по сети открытым HTTP). **[тест]**
* Приложение: `network_security_config` разрешает cleartext только для `127.0.0.1`, `localhost`, `10.0.2.2`; для остальных адресов приложение само требует `https://`. **[тест]** (Robolectric: «rejects remote plain http»)
* Заголовки ответов: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Cache-Control: no-store`; ошибки — структурированные, без стектрейсов. **[тест]**
* Swagger UI доступен на `/api/docs` — только через тот же локальный адрес.
* Бот — только исходящие соединения к `api.telegram.org` (long polling), входящих портов не открывает.

## 7. Обработка ввода
* Все тела запросов — Pydantic-модели с ограничениями длины/диапазонов; настройки валидируются по схеме (тип, диапазон, длина). **[тест]**
* SQL — только параметризованные запросы. **[код]**
* FFmpeg запускается списком аргументов (без shell), с таймаутом, лимитом потоков, лимитом размера входа (20 МБ) и длительности; временные файлы в `data/tmp`, удаляются после задачи; имена файлов генерируются сервером. **[тест]**
* Калькулятор — собственный парсер (Pratt), без `eval`; ограничения степени/факториала/длины. **[тест]**
* Правила автоматизации и пользовательские команды — декларативные (JSON-схема), без выполнения кода; `validate_rule` отклоняет неизвестные триггеры/действия; dry-run ничего не отправляет. **[тест]**
* Тексты для Telegram экранируются (HTML parse mode). **[код]**

## 8. Telegram Business: безопасное поведение
* Защита от петель: сообщения с `sender_business_bot` (отправленные самим ботом) не обрабатываются как входящие; дедупликация апдейтов (LRU + БД). **[тест]**
* Перед действием проверяются права подключения; при их отсутствии — понятное сообщение владельцу, а не ошибка. **[тест]**
* Опасные права (`can_transfer_stars`, `can_transfer_and_upgrade_gifts`, `can_convert_gifts_to_stars`, `can_change_gift_settings`, `can_edit_username`) **не используются**; инспектор прав предупреждает, если они выданы. Передача Stars/подарков не реализована. **[тест]**
* Аварийная остановка (`emergency_stop`) и режим обслуживания сразу прекращают автоматические ответы. **[тест]**
* Flood control: ~1 сообщение/с на чат и ~25/с глобально, учёт `retry_after` **[тест]**; рассылки — только в личку бота, 20 сообщений/с, только администраторы **[код]/[тест]**.

## 9. Платежи (Telegram Stars)
* По умолчанию `PAYMENTS_ENABLED=false` — счета не выставляются. **[тест]**
* `pre_checkout_query` проверяет тариф, сумму и валюту XTR; повторный `successful_payment` с тем же `telegram_payment_charge_id` не продлевает подписку дважды. **[тест]**
* Возврат (`refundStarPayment`) — только Super Admin, с записью в аудит. **[код]**
* Нет «фейковых успешных оплат»: подписка выдаётся только по `successful_payment` или вручную администратором (с аудитом).

## 10. Приватность
* История переписки хранится ограниченно (по умолчанию 7 дней, можно 0), превью можно отключить. **[тест]**
* Долгосрочная память AI — только по явной команде/настройке, факты удаляются по TTL. **[код]**
* Экспорт и удаление своих данных — в боте и в приложении. **[тест]**
* Администратор видит метаданные (пользователи, тарифы, статистику), но API не отдаёт администраторам содержимое чужих переписок. **[код]**
* AI-ответы собеседникам помечаются (`ai_disclosure`), если включён AI-режим.

## 11. Android-приложение
* `allowBackup="false"`; токены в Android Keystore (AES-GCM, ключ не экспортируется); при ошибке расшифровки сессия сбрасывается. **[код]**, Keystore на реальном телефоне — **[устройство]**
* Единственное разрешение — `INTERNET`. Нет WebView, нет сторонних SDK и аналитики. **[проверено]** (`aapt2 dump badging`, TEST_REPORT §3)
* Автообновление access-токена через refresh; если refresh недействителен — выход на экран привязки. **[код]**

## 12. Остаточные риски (честно)
| Риск | Комментарий / смягчение |
|---|---|
| Любое приложение на телефоне может обратиться к `127.0.0.1:8787` | Без действующего токена получит только `/health`; перебор кодов ограничен (п. 4). |
| `.env` и БД не зашифрованы на диске | Защищены песочницей Termux (другие приложения без root не читают). На рутованном телефоне защита слабее. |
| Ключ подписи для `build_apk.sh` по умолчанию с паролем `chathelper` | Ключ создаётся локально и не попадает в git; для своих релизов задайте `KS_PASS`. |
| Удалённый режим API | Выключен; при включении нужен свой TLS-сертификат и осознанная настройка сети. |
| Сторонние AI-провайдеры получают текст запросов | Только при настроенном ключе и включённых AI-функциях; это явно описано в панели «Приватность». |
| Работа с реальным Telegram и на реальном устройстве | Не проверялась в среде разработки (нет доступа к api.telegram.org и к телефону) — см. [FEATURE_MATRIX.md](FEATURE_MATRIX.md). |

## 13. Как сообщить о проблеме
Владельцу бота: меню → «Поддержка» или `.support`. Не публикуйте токены, коды привязки и логи без маскировки.
